### Domain Specifications Index

| `BR-002` | Snapshot Isolation by Commit Sequence, First-Updater-Wins Conflicts, `NO-STEAL` Staging & Commit-Order WAL Durability | Every commit observed by the engine gets the next commit sequence number (`Mark_Committed`); a snapshot (`Take_Snapshot`) is the last number taken. A version `(Xmin, Xmax)` is visible to snapshot `S` iff `Xmin` committed with sequence `<= S` and `Xmax` is `0`, uncommitted, or committed with sequence `> S` (`Is_Version_Visible`); uncommitted versions are never visible, the writer's own included. A write to a document holding another active transaction's version is refused with `Status_Tx_Aborted` (`Has_Write_Conflict`). Updates keep the single prior committed version (`Has_Prior_Version`) for older snapshots and rollback; rolling back an update that had displaced an older prior version cannot resurrect it. Active transactions stage pages only as `WAL_Frame_Data` frames (`NO-STEAL`); the durable `WAL_Frame_Commit` append is the commit point, after which `Commit_Tx` reports `Status_Ok` (and `Flush_Pending` if `.db` must still be repaired by redo). Page 1 of a commit carries only committed versions and the committing transaction's own. Recovery repairs torn WAL / `.db` tails, replays in commit order, and reports `Max_Seen_Tx` so transaction ids are never reused (`ADR-009`, `ADR-010`). | `src/nhe_o-transaction.ads`, `src/nhe_o-rag.ads`, [`storage-and-wal-format.md`](storage-and-wal-format.md) |
| `BR-003` | PostgreSQL Vector, Scale-Aware Quantization & PostgreSQL-Exact JSONB | Vector distance operators (`<->`, `<=>`, `<#>`, Hamming) require matching dimensions (`1 .. 4096`) and bounded finite components `[-1.0e6 .. 1.0e6]`; cosine distance is scale invariant (exactly `1.0` when a vector is all zero), `Int8` SQ8 is scale-aware with saturating dequantization, and retrieval returns the exact top-K. JSON must pass RFC 8259 validation with well-formed UTF-8 (surrogates only as `\u` pairs, no U+0000). Stored JSONB documents are objects of at most `512` bytes with at most `16` distinct top-level keys (a duplicate key keeps the last value), keys of `1 .. 64` bytes at every depth, at most `64` nesting levels including the root, and numbers inside PostgreSQL's `numeric` range. `->` returns the re-escaped JSON value, `->>` the decoded text (`Is_Null` for JSON `null`), `?` tests a top-level key, and `@>` follows PostgreSQL containment at every depth (scalars by value with exact numeric equality, objects key by key, arrays element-wise) (`ADR-003`, `ADR-015`, `ADR-017`). | `src/nhe_o-vector.ads`, `src/nhe_o-hnsw.ads`, `src/nhe_o-json.ads` |
| `BR-004` | Key-Value TTL, Bounded LRU Eviction & Slot-Exact `"KVMG"` WAL Durability | Every operation takes the caller's timestamp `Now` (non-decreasing). An entry with a TTL is expired when `Now >= Expires_At` and is never returned by `Get`, `Exists` or `TTL`; reads report it (`Status_Expired`) but never free it, so only logged writes change the slot layout. A SET first frees the key's own entry and then takes the first free slot, else the first expired slot, else the least recently used one (lowest slot on ties) of the `64` slots; `INCRBY` of an absent or expired key reuses that key's slot when it still holds one. `DEL` at `Now` reports a removal only for a live key but frees expired entries too. `INCRBY` accepts Redis `string2ll` integers only (no `+`, no leading zeros, no `-0`) and rejects overflow. Durable variants append a slot-hinted `WAL_Frame_KV` record (`"KVMG"`, CRC32) before acknowledging and roll the store back on WAL failure; `Recover_KV_From_WAL` applies each hinted SET to exactly its slot, so recovery reproduces keys, values, TTLs and slot layout including silent evictions. Read recency (`Last_Access` updated by `Get`) is not logged: after a reopen it is the time of the last durable write or checkpoint. Deliberate Redis deviations: `EXPIRE` with a TTL `<= 0` is rejected (Redis deletes the key) and a SET with TTL `0` means no TTL (`ADR-007`, `ADR-014`). | `src/nhe_o-kv.ads`, [`storage-and-wal-format.md`](storage-and-wal-format.md) |
| `BR-005` | Dual-Mode Pub/Sub Delivery, `Owner_Tx` Guard & Overflow Accounting | Standard channels deliver messages in FIFO order immediately to matching active subscribers (exact channel or general `*` glob wildcard pattern at any position) in bounded ring buffers, incrementing `Dropped` if a subscriber's ring is full. `Durable` transactional notifications (`Stage_Notify`) verify `Staging.Owner_Tx = Ctx.Id` and are dispatched to subscribers iff `Ctx.State = Tx_Committed` (`Flush_Committed_Notifications`), or discarded by the owning transaction on `Rollback_Tx` (`ADR-004`). | `src/nhe_o-pubsub.ads`, `src/nhe_o-transaction.ads` |
| `BR-006` | 4KB `"SLOT"` Primary Pages, `"TOAS"` Overflow Chains, `"RMET"` Metadata & `"VTST"` Stage-2 Vector Re-Ranking | Primary tuples reside in 4096-byte `"SLOT"` slotted pages with 24B CRC32 headers and 16×8B line pointer directories. Oversized parent chunks, extended `Summary_Text` (`> 63B`) or `JSONB_Document` metadata exceeding inline limits (`Encode_Meta_TOAST`, `"RMET"` header), and the full embedding of every document (`Encode_Vector_TOAST`, `8B` `"VTST"` header + one 32-bit scaled-decimal word per component, 16 exponent codes, about 7 significant digits, up to `16,392` bytes) are persisted across non-overlapping contiguous linked 4KB `"TOAS"` overflow pages referenced by 16-byte `TOAST_Pointer` values, verified on startup recovery and Stage-2/Stage-3 RAG execution (`ADR-003`, `ADR-006`). | `src/nhe_o-transaction.ads`, `src/nhe_o-vector.ads`, `src/nhe_o-rag.ads`, [`storage-and-wal-format.md`](storage-and-wal-format.md) |
