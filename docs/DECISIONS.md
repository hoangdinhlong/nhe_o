## ADR-001 — Unified Multi-Model Engine (PostgreSQL SQL/JSONB/Vector + Redis KV & Pub/Sub over Shared MVCC/WAL)
- **Status:** Partially superseded — KV entries are WAL-logged slots without MVCC (`ADR-007`, `ADR-014`), and MVCC visibility belongs to the RAG engine by commit sequence numbers (`ADR-010`); the shared WAL and the one-engine design stand.
- **Decision:** Build Nhé O (crate `nhe_o`, Ada root package `Nhe_O`) as a single in-process multi-model engine where PostgreSQL relational tables, `VECTOR(d)` embeddings, `JSONB` documents, and Redis-compatible Key-Value cache entries share a unified 4096-byte slotted-page layout, header-and-payload CRC32-verified Write-Ahead Log (WAL), and MVCC snapshot isolation (`xmin`/`xmax`), paired with a bounded ring-buffer Pub/Sub broker.
- **Why:** Running separate SQLite, `pgvector`, and Redis processes for embedded or local-first workloads adds operational overhead and cross-store consistency bugs. Sharing one ACID storage and WAL engine guarantees crash-safe durability across relational, vector, document, and KV mutations while allowing direct KV and Pub/Sub calls to bypass SQL parsing overhead.
- **Consequences:** `Nhe_O.Types` defines the canonical PostgreSQL type tags (used by the SQL validator) and the bounded text types every subsystem shares; `Nhe_O.Transaction` governs transaction IDs (`Tx_Id`), the CLOG and WAL frame encoding/decoding/verification for every model. As built in `v0.4.0`, KV entries live in in-memory slots logged as `"KVMG"` WAL frames with their own sequence ids and no MVCC (`ADR-007`, `ADR-014`), and MVCC snapshot visibility is `Nhe_O.RAG.Is_Version_Visible` (`ADR-010`).

## ADR-002 — 100% SPARK_Mode (On) Mandate via Statically Bounded Memory and Contract-Bound POSIX Syscall I/O
- **Date:** 2026-10-16
- **Decision:** Enforce `pragma SPARK_Mode (On);` across 100% of specifications, bodies, and entrypoints (`src/*.ads` and `src/*.adb`, 26/26 files). Use statically bounded containers (zero dynamic heap allocation) and bind `Nhe_O.IO` (`src/nhe_o-io.ad[sb]`) directly in `SPARK_Mode (On)` (`Convention => C, Import => True, Side_Effects`) to atomic, exception-free POSIX syscalls (`open`, `pread`, `pwrite`, `lseek`, `fsync`, `close`, `unlink`, `access`) and `Ada.Text_IO`.
- **Why:** Standard Ada file libraries (`Ada.Direct_IO`, `Ada.Streams.Stream_IO`) report I/O errors by raising Ada exceptions, which would force the physical I/O body out of SPARK (`SPARK_Mode (Off)`). Binding directly to POSIX C syscalls — which never raise Ada exceptions and instead return explicit status/byte counts (`int` / `ssize_t`) — keeps 100% of I/O orchestration (`To_C_Path`, embedded-NUL path rejection, 64-bit page offset bounds `Valid_Page_Id`, short-read/write detection, bounded `EINTR` retry loops, and `fsync` checks) inside `SPARK_Mode (On)`.
- **Consequences:** Zero files in `src/` may use `pragma SPARK_Mode (Off);` (`BR-001`, mechanically enforced by `SELF-AUDIT.md` check `B5`). All buffers, pages, vectors, JSONB documents, KV slots, and Pub/Sub rings use fixed capacity bounds without exception propagation. *(See lesson: [`learning/swe/01-contract-bound-posix-syscalls-in-spark.md`](learning/swe/01-contract-bound-posix-syscalls-in-spark.md)).*

## ADR-003 — 4KB Slotted Pages with TOAST Overflow Chains, 4096-D Vectors & Quantization for Universal RAG
- **Date:** 2026-10-17
- **Decision:** Retain 4096-byte primary slotted pages while introducing PostgreSQL-style TOAST overflow page chains (`TOAST_Pointer` / `Root_Overflow_Page`) for oversized attributes (high-dimensional embeddings and parent-document RAG chunks), expanding `Max_Vector_Dim` up to `4096`, and supporting Scalar (`Int8`) and Binary (`1-bit` Hamming) vector quantization alongside `Float32` (`<->`, `<=>`, `<#>`) for HNSW and Hybrid RAG.
- **Why:** Local LLM workflows (e.g., Qwen 3.8 27B, Qwen 3.8 35B-A3B) and modern embedding models (`bge-m3` 1024-D, `text-embedding-3-large` 3072-D, `Qwen3-Embedding-8B` 4096-D = 16KB raw `Float32`) paired with multi-kilobyte text chunks exceed any single 4KB or 16KB page. Keeping 4KB primary pages aligns with OS/NVMe page boundaries and allows fast relational/JSONB metadata filtering over compact 16-byte TOAST pointers without reading cold vector payloads, while `Int8`/Binary quantization reduces HNSW RAM usage by 4x–32x so the database coexists with large local LLMs.
- **Consequences:** Resolves `Q-001`. `Nhe_O.Transaction` gains linked 4KB TOAST overflow pages (`BR-006`); `Nhe_O.Vector` scales up to 4096 dimensions with `Float32`, `Int8`, and `Binary` quantization (`BR-003`) in Epic 02. *(See lesson: [`learning/ai/01-toast-overflow-and-vector-quantization-for-local-llm-rag.md`](learning/ai/01-toast-overflow-and-vector-quantization-for-local-llm-rag.md)).*

## ADR-004 — Dual-Mode Pub/Sub: Fast In-Memory Ring Buffers + Optional `DURABLE` WAL-Committed Dispatch
- **Date:** 2026-10-17
- **Decision:** Support two delivery semantics in `Nhe_O.PubSub`: (1) default low-latency in-memory ring-buffer delivery (Redis `PUBLISH`/`SUBSCRIBE` semantics), and (2) optional `Durable` transactional delivery (PostgreSQL `LISTEN`/`NOTIFY` semantics) where staged notifications are dispatched to subscribers only after `Nhe_O.Transaction.Commit_Tx` flushes the transaction's WAL frame to disk, or discarded on `Rollback_Tx`.
- **Why:** Agentic RAG and local LLM applications require both instantaneous ephemeral event streaming between agents and crash-safe transactional triggers (ensuring background RAG embedding/HNSW workers never index uncommitted or rolled-back document chunks).
- **Consequences:** Resolves `Q-002`. `Nhe_O.PubSub` and `Nhe_O.Transaction` coordinate transactional notification staging and post-WAL-commit dispatch (`BR-005`) in Epic 02. *(See lesson: [`learning/swe/02-transactional-pubsub-wal-commit-barrier.md`](learning/swe/02-transactional-pubsub-wal-commit-barrier.md)).*

## ADR-005 — Formally Verified C ABI / FFI Boundary via Precondition-Free Defensive Subprograms in 100% SPARK
- **Date:** 2026-10-17
- **Decision:** Expose the embedded C / Python Foreign Function Interface (`Nhe_O.C_API` in `src/nhe_o-c_api.ad[sb]`, C header `include/nhe_o.h`, Stand-Alone Shared Library `nhe_o_lib.gpr` -> `lib/libnhe_o.so`, and Python SDK `bindings/python/nhe_o.py`) in 100% `pragma SPARK_Mode (On);` using fixed-capacity `Interfaces.C.char_array` buffers paired with explicit integer lengths and precondition-free (`Pre => True`) exported procedures that defensively validate every untrusted C argument before invoking internal SPARK engines.
- **Why:** Raw C pointers (`Interfaces.C.Strings.chars_ptr`) violate SPARK's ownership and aliasing model and would force `SPARK_Mode (Off)`, while placing SPARK `Pre` contracts on exported `Convention => C` subprograms cannot be statically verified against external C or Python callers. Passing fixed-bound `char_array` buffers by reference (`const char *` / `char *` in C ABI) and validating all scalar lengths, ranges, and floating-point bounds inside the exported wrapper guarantees that `gnatprove` proves 100% Absence of Run-Time Errors (AoRTE) across the FFI boundary regardless of what values an external caller passes.
- **Consequences:** All 26 source files (`src/*.ads` and `src/*.adb`) remain in 100% `SPARK_Mode (On)` (`BR-001`) and achieve 100% formal verification (`0 unproved` checks in `gnatprove`), while Python (`ctypes`), C, C++, and Rust applications can load `lib/libnhe_o.so` directly. *(See lessons: [`learning/swe/03-precondition-free-defensive-c-ffi-in-spark.md`](learning/swe/03-precondition-free-defensive-c-ffi-in-spark.md), [`learning/swe/04-proving-ieee754-float-and-loop-invariants-in-spark.md`](learning/swe/04-proving-ieee754-float-and-loop-invariants-in-spark.md)).*

## ADR-006 — NO-STEAL WAL Staging, 2-Pass Committed-Only WAL Recovery, Unified 8192-Entry CLOG, Primary `"SLOT"` Pages & `"VTST"` / `"RMET"` TOAST Chains
- **Status:** Partially superseded — recovery order and torn-file handling by `ADR-009`, snapshot rule by `ADR-010`, vector payload encoding and scope by `ADR-018`.
- **Date:** 2026-10-17
- **Decision:** (1) Enforce **NO-STEAL** page persistence: `Write_TOAST_Chain`, `Ingest_Document`, and `Delete_Document` stage 4KB `"TOAS"` and `"SLOT"` pages exclusively as `WAL_Frame_Data` (`0`) frames in `.wal` while `Ctx.State = Tx_Active`, and `Commit_Tx` pre-scans all frames up to `Max_WAL_Scan_Frames = Max_WAL_Frames = 4096` (`Hit_EOF` check + `Posix_Lseek SEEK_END` 4120B file-size alignment verification), verifies `Verify_WAL_Frame` CRC32 on every frame, rejects duplicate or post-commit frames for `Tx.Id`, and materializes staged pages to `.db` only after flushing the `WAL_Frame_Commit` (`1`) barrier frame; (2) unify `Max_CLOG_Entries = Max_Tx_Id = 8192`, initialize `Default_CLOG := [others => Tx_Idle]`, prevent `G_Next_Tx` wraparound at `Max_Tx_Id`, and run `Redo_WAL_Recovery` in two passes (Pass 1 discovers `WAL_Frame_Commit` records; Pass 2 replays only committed transactions); (3) persist primary tuples in 4096-byte `"SLOT"` slotted pages (`240 B` tuple cell / `208 B` `Inline_Data` with strict `Free_Lower`/`Free_Upper`/unoccupied-slot verification) paired with optional `"RMET"` extended summary + JSONB metadata TOAST chains (lossless up to `512 B` summary + `16 × (64 B key, 512 B val)` JSONB), startup & Stage-3 parent-chunk TOAST verification, and pairwise non-overlapping `Ranges_Overlap` / `Is_TOAST_Range_Free` page allocation; and (4) combine Stage-1 HNSW routing (64-D Matryoshka `Float32`/`Int8` with `Int8_Scale` + 4096-D `Binary`, synchronized across in-place deduplicating `Insert_Vector`/`Remove_Vector`/`Restore_Vector_Node`) with Stage-2 Exact L2 Re-Ranking from `"VTST"` 4KB TOAST overflow chains (`8B` `"VTST"` + `Dim` header + 15-tier scientific `Float32` words retaining 7–8 significant decimal digits up to `16,392` bytes).
- **Why:** Writing dirty pages directly to `.db` before `Commit_Tx` without an `UNDO` log or defaulting `CLOG` to `Tx_Committed` violates ACID atomicity and snapshot isolation. Furthermore, persisting full `> 64`-D `Float32` embeddings in `"VTST"` TOAST chains and full `Summary_Text`/`Metadata` in `"RMET"` TOAST chains (`Q-003`) while keeping compact 64-D + 1-bit representations in RAM gives HNSW sub-millisecond RAM efficiency without sacrificing exact 4096-D top-$K$ precision or truncating document metadata on Page 1.
- **Consequences:** Resolves `Q-003` and codifies the core storage, MVCC, and two-stage RAG durability architecture verified across Epic 04 (`docs/epics/04-post-epic-03-grooming-and-hardening/ADVERSARIAL-REVIEW.md`, `docs/domain/storage-and-wal-format.md`, `BR-002`, and `BR-006`). *(See lessons: [`learning/swe/05-two-pass-wal-recovery-and-slotted-page-crc32-in-spark.md`](learning/swe/05-two-pass-wal-recovery-and-slotted-page-crc32-in-spark.md), [`learning/swe/06-two-stage-toast-vector-reranking-and-hnsw-pruning.md`](learning/swe/06-two-stage-toast-vector-reranking-and-hnsw-pruning.md), [`learning/swe/07-closing-protocol-invariant-gaps-and-modular-spark-contracts.md`](learning/swe/07-closing-protocol-invariant-gaps-and-modular-spark-contracts.md), [`learning/swe/09-eliminating-tautological-contracts-and-contextual-inlining-in-spark.md`](learning/swe/09-eliminating-tautological-contracts-and-contextual-inlining-in-spark.md)).*

## ADR-007 — Dual-Mode Key-Value Store (In-Memory Cache + `"KVMG"` WAL-Before-Data Persistence) & Feature → Grooming Epic Cadence
- **Date:** 2026-10-17
- **Decision:** (1) Keep `Nhe_O.KV.Set`/`Get`/`Del`/`Expire`/`Incr_By` as `Global => null` in-memory operations for sub-microsecond Redis cache workloads while adding `Set_Durable`, `Del_Durable`, `Expire_Durable`, `Incr_By_Durable`, and `Recover_KV_From_WAL` (`WAL_Frame_KV` with `"KVMG"` page magic, IEEE 802.3 CRC32, `Store := Saved_Store` rollback on both WAL write failure and mid-recovery corruption, dedicated `G_Next_KV_Seq` sequence numbering in `Nhe_O.C_API` decoupled from MVCC `G_Next_Tx`, and `Max_Frames` overflow / torn-file detection) for crash-recoverable KV state (`Q-004`); and (2) adopt a mandatory **Feature Epic → Grooming Epic** cadence in `AGENTS.md` and `docs/epics/README.md` so every feature epic milestone is audited (`ADVERSARIAL-REVIEW.md`) and hardened before the next feature epic begins.

- **Consequences:** Resolves `Q-004` and codifies the durable KV protocol in `BR-004` and `docs/domain/storage-and-wal-format.md`. ## ADR-008 — Native Labeled Property Graph Engine (`Nhe_O.Graph`), Bi-Directional CSR Adjacency (`"GRPH"`), `SQL/PGQ MATCH` & Multi-Hop GraphRAG
- **Date:** 2026-10-19
- **Decision:** Upgrade Nhé O from a single-edge `1-Hop Related_Doc_Id` pointer to a first-class, 100% formally verified **Labeled Property Graph (LPG) Engine (`Nhe_O.Graph`)** on par with Neo4j and Apache AGE in core graph power, scheduled as **Epic 06 (`06-property-graph-and-multi-hop-graphrag`)** immediately after Epic 05 (`Catalog`, `Buffer_Pool`, `Executor`):
  1. **Data Model & Storage (`"GRPH"` 4KB Pages + MVCC)**: Support typed Vertices (`Vertex_Id`, `Label`, `JSONB_Document` properties, optional `Vector_Id` / `Doc_Id` binding, `MVCC_Tuple_Header`) and Directed Weighted Edges (`Edge_Id`, `Src_Vertex`, `Dst_Vertex`, `Edge_Label`, `Float32 Weight`, `JSONB_Document` properties, `MVCC_Tuple_Header`) persisted in 4096-byte CRC32-verified `"GRPH"` pages managed by `Nhe_O.Buffer_Pool` and `Nhe_O.Transaction` (`NO-STEAL` WAL + `CLOG`).
  2. **Bi-Directional Index-Based Adjacency (`Out_Edges` & `In_Edges` / CSR)**: Maintain $O(1)$ outgoing and incoming edge chains per vertex via array indices (`First_Out_Edge`, `Next_Out_Edge`, `First_In_Edge`, `Next_In_Edge`).
  3. **Core Graph Operators & `Always_Terminates` Proofs**: Implement multi-hop pattern matching (`1..k` hops, outgoing `->`, incoming `<-`, bidirectional `-`), variable-length reachability (`BFS` with vertex/edge label and `JSONB @>` predicates), unweighted & weighted Shortest Path (`BFS` / `Dijkstra`), Mutual Neighbors / Triangle Discovery ($N(u) \cap N(v)$ for social graphs and community detection), Degree/PageRank centrality, and **Multi-Hop GraphRAG Score Propagation** coupled with 4096-D `Nhe_O.HNSW`.
  4. **Query Surface (`SQL/PGQ MATCH` + Native Composable FFI API)**: Support ISO SQL:2023 `SQL/PGQ` `MATCH (a:Label)-[e:TYPE*1..k]->(b:Label)` patterns directly inside `Nhe_O.SQL` (`SELECT ... MATCH ... WHERE meta @> ... ORDER BY emb <=> $1`) alongside zero-parse-overhead C ABI / Python SDK primitives (`nhe_o_graph_upsert_vertex`, `nhe_o_graph_upsert_edge`, `nhe_o_graph_traverse_bfs`, `nhe_o_graph_shortest_path`, `nhe_o_graph_mutual_neighbors`, `nhe_o_rag_graph_query`).
- **Why:** A true Property Graph pillar serves both as a standalone capability (Social Networks, ReBAC permissions, Fraud/Lineage graphs) and as a **force multiplier for every original Nhé O pillar**: it elevates `Nhe_O.RAG` from flat vector lookup to true multi-hop Knowledge GraphRAG, eliminates expensive recursive SQL `JOIN`s in `Nhe_O.SQL`/`Nhe_O.BTree` via $O(1)$ adjacency hops, pairs with `Nhe_O.KV` for real-time per-vertex counters/TTL state, and enables graph-routed notifications in `Nhe_O.PubSub` — completing the 5-model embedded architecture (`Relational + JSONB + 4096-D Vector + Property Graph + Redis KV/PubSub`) in a single `< 300 KB` `100% SPARK_Mode (On)` library.
- **Technical Challenges / Disadvantages & Formal Mitigations:**
  1. **SPARK Anti-Aliasing Mandate vs. Heap Pointer-Chasing**: Neo4j relies on Cyclic Heap Pointers ("index-free adjacency"), which SPARK forbids (`BR-001`). *Mitigation:* Use KùzuDB-style **Array-Indexed Double-Linked Adjacency Lists / Compressed Sparse Row (CSR)** over 4KB `"GRPH"` pages, which is 100% SPARK-provable, eliminates dangling pointers, and improves CPU L1/L2 cache locality over JVM pointer chasing.
  2. **Cypher Scripting Surface Bloat vs. Parser VC Complexity**: Implementing all of Neo4j's `openCypher` scripting conveniences (`UNWIND` list comprehensions, `APOC` procedures, arbitrary multi-`WITH` pipelines) would bloat the parser and slow down `gnatprove`. *Mitigation:* Support the declarative core via ISO SQL:2023 `SQL/PGQ` `MATCH (a)-[e]->(b)` inside `Nhe_O.SQL` while exposing composable native graph operators over the in-process C ABI / Python SDK (zero TCP round-trip overhead).
  3. **Static RAM Footprint Risk if Coupled into `RAG_Engine`**: Embedding multi-edge adjacency arrays inside every `RAG_Document_Entry` would inflate `RAG_Engine` for non-graph workloads. *Mitigation:* Build `Nhe_O.Graph` as a decoupled sibling package (`src/nhe_o-graph.ad[sb]`) backed by 4KB `"GRPH"` pages through Epic 05's `Nhe_O.Buffer_Pool`, leaving existing `KV`, `Vector`, `HNSW`, and basic `RAG` footprints untouched.
  4. **Cyclic Graph Infinite Loops & SMT Solver Timeouts**: Cyclic graphs (`A -> B -> A`) can hang naive traversals and explode SMT proof obligations. *Mitigation:* Enforce iterative bounded-queue `BFS` / `Dijkstra` with explicit `Visited_Vertex_Set` boolean arrays, decreasing `Loop_Variant`s (`Always_Terminates`), and modular helper contracts (`with Post => ..., Global => null`, per Lesson 07).
- **Consequences:** Codified in `BR-008`, `VISION.md`, `ARCHITECTURE.md`, Lesson 08 (`docs/learning/swe/08-formally-verified-property-graph-csr-and-sql-pgq-in-spark.md`), and scheduled in `docs/epics/06-property-graph-and-multi-hop-graphrag/PROGRESS.md`.


## ADR-009 — Crash-Consistent WAL Protocol v2: Durable-Barrier Commit Point, Torn-Tail Repair & Commit-Order Redo
- **Date:** 2026-10-20
- **Decision:** (1) The commit point of a transaction is the durable append of its `WAL_Frame_Commit` barrier: once it is appended `Commit_Tx` returns `Status_Ok` even if materializing the staged pages into `.db` fails, and reports `Flush_Pending` so the caller repairs `.db` with `Redo_WAL_Recovery` (`Commit_RAG_Tx` does so in place). (2) `Append_WAL_Frame` reports success only for a durable frame and otherwise truncates the WAL back (best effort). (3) Every recovery first runs `Repair_WAL_Tail` and `Repair_DB_Tail`: the torn last WAL frame (partial, or a bad final frame) and a partial last `.db` page are truncated, after classifying the whole file so that a non-WAL file or mid-log corruption fails closed untouched. (4) `Redo_WAL_Recovery` replays in **commit order** (per barrier: the data frames staged before it, then its page) and ignores data frames after their own barrier. (5) `Max_Seen_Tx` covers every data and commit frame, committed or not, and callers seed new transaction ids above it.
- **Why:** Round 12 reproduced that a torn WAL tail, a CRC-bad final frame, or a torn `.db` tail made a database permanently unopenable; that a failure after a durable barrier was reported as an abort yet resurrected by recovery (phantom commit); that WAL-order redo diverged from run-time materialization when two transactions wrote the same page; and that reusing the id of a crashed transaction let a later commit adopt its orphan frames.
- **Consequences:** Supersedes the "2-pass committed-only replay in WAL order" and "torn files fail closed" parts of `ADR-006`. Status semantics: `Status_Ok` from `Commit_Tx` means durable; `Status_IO_Error` means "decided by the next recovery" (the rollback truncation can itself fail). Specified in `docs/domain/storage-and-wal-format.md` §1 and `BR-002`. Round 15: the first frame of an empty WAL is written in two synced steps (its first 512-byte sector, then the whole frame), and a lone torn frame may also be a prefix of a frame header shorter than 24 bytes, so a tear inside the header of the first frame of a WAL or of a `"<wal>.ckpt"` is always recognized as a torn append.

## ADR-010 — Snapshot Isolation by Commit Sequence Numbers & First-Updater-Wins Write Conflicts
- **Date:** 2026-10-20
- **Decision:** MVCC visibility in `Nhe_O.RAG` uses commit sequence numbers instead of transaction ids: `Mark_Committed` gives each commit the next number, a snapshot (`Take_Snapshot`) is the last number taken, and `Is_Version_Visible` shows a version iff its creator committed at or before the snapshot and its deleter (if any) did not. Uncommitted versions are never visible, including the reader's own. Writers pass the snapshot they took when they started (`Ingest_Document` / `Delete_Document` take `Snapshot`), and a write fails with `Status_Tx_Aborted` (`Has_Write_Conflict`) when the document's newest version was created or deleted by a concurrent writer: another transaction that is still active (first updater wins) or one that committed after the writer's snapshot (no lost update, as PostgreSQL `REPEATABLE READ` reports a serialization failure). `Build_RAG_Slotted_Page` persists only committed versions or the committing transaction's own, a failed ingest truncates its WAL frames or poisons its transaction (`CLOG := Tx_Aborted`) so they can never be committed, and `Commit_RAG_Tx` wraps the commit protocol. Versions recovered from disk or frozen by a checkpoint carry sequence number `0`.
- **Why:** Transaction-id snapshots are not snapshot isolation: a transaction with a smaller id that commits later became visible to an older snapshot. Round 12 also showed lost updates without conflict detection and a commit's Page 1 carrying another transaction's uncommitted version, which recovery then treated as committed.
- **Consequences:** Supersedes the tx-id snapshot rule of `ADR-006` / `BR-002` (the 2-argument `Is_Tuple_Visible` was removed; the CLOG-only 3-argument rule remains for raw tuples). Each document keeps a single prior version. Since Round 14, an update that drops the prior raises `Read_Horizon` to the commit sequence of the version kept, and a query at an older snapshot fails with `Status_Tx_Aborted` ("snapshot too old", like Oracle's undo retention) instead of silently missing the document; a rollback cannot resurrect the dropped version, so the horizon stays until a freeze or recovery. The C ABI takes each snapshot inside one call and is never affected. Round 13 added the writer snapshot (lost updates and deletes of versions committed after the snapshot were accepted), the immediate rollback of a poisoned transaction's versions (a later committed delete of such a version was lost), and the collapse of a deleted own new version back to its prior version (the single prior-version slot could otherwise end up holding a version no snapshot sees).

## ADR-011 — WAL Checkpoint: Freeze, Atomic WAL Replacement & Automatic Thresholds
- **Date:** 2026-10-20
- **Decision:** `nhe_o_checkpoint` (`C_Checkpoint`) compacts the WAL: `Freeze_RAG_Engine` (VACUUM FREEZE on a static scratch copy: deleted documents and prior versions dropped, every live version re-stamped as transaction `1`, CLOG reset) and a new WAL `"<wal>.ckpt"`, created with `O_EXCL`, holding one slot-hinted `"KVMG"` SET frame per occupied KV slot plus a commit frame of transaction `1` with the frozen Page 1; then `rename(2)` over the live WAL and `fsync` of its directory. The rename is the commit point; transaction ids restart at `2`. It runs automatically after a durable write once the WAL holds `512` frames or a transaction / KV sequence id reaches `4096`, and at open time (which also rescues databases whose id space an older version exhausted).
- **Why:** Without compaction the engine had a lifetime budget of `4096` WAL frames and `8191` transaction ids, after which every write failed for good, and every commit re-scanned an ever-growing WAL.
- **Consequences:** Every crash point recovers to the same logical database (old WAL before the rename, new WAL after it; Page 1 of `.db` is rewritten by the next commit or by redo). Refused while the write-fault latch is set (`ADR-012`). The database path may not equal `"<wal>.ckpt"`. `Freeze_RAG_Engine` alone is not a checkpoint: ids may restart at `2` only after the WAL has been replaced (an old frame of a reused id would be replayed or would abort the new commit), and every snapshot taken before a freeze is invalid afterwards (frozen versions carry sequence `0`); the C ABI takes every snapshot inside one call. Since Round 14, `Freeze_RAG_Engine` also refuses (`Status_IO_Error`) while a commit left pages unmaterialized (`Pages_Pending`), because the WAL a checkpoint replaces would hold their only copy.

## ADR-012 — Write-Fault Latch After Durable I/O Errors (fsync-Failure Policy)
- **Date:** 2026-10-20
- **Decision:** In the C ABI, any `Status_IO_Error` on a durable write path, a commit whose pages could not be materialized (`Flush_Pending` still set after the in-place redo), or a failed directory `fsync` after the checkpoint rename sets `G_Write_Fault`. From then on every write returns `NHE_O_STATUS_IO_ERROR` until `nhe_o_init_with_paths` reopens the database and recovery re-derives the durable state from disk. KV and Pub/Sub reads keep serving memory; RAG queries read TOAST pages from the database file, so after a commit whose pages could not be materialized they fail with `NHE_O_STATUS_IO_ERROR` until the reopen (Round 15).
- **Why:** After a failed `fsync`, Linux may already have dropped the dirty pages, so retrying cannot prove durability (the PostgreSQL "fsyncgate" lesson). Continuing to write after such a failure would let the in-memory state drift from what a crash would recover.
- **Consequences:** A failed write's outcome is "decided by the next recovery" (documented in `include/nhe_o.h`). Transient errors (e.g. `EMFILE`) also latch; reopening clears the latch.

## ADR-013 — C ABI 0.4 Runtime Model: One Process-Wide Engine, Serialized Calls, Safe Scratch Files & Proof-Based Library Build
- **Date:** 2026-10-20
- **Decision:** (1) The library drives one process-wide engine and is not thread-safe; the Python SDK serializes every call through a process-wide lock and allows one open `NheOEngine` per process (`close()` / context manager), using a private `mkdtemp` directory for non-3-D scratch databases. (2) `nhe_o_init` uses per-process scratch files `/tmp/nhe_o_c_api.<pid>.db` / `.wal`, recreated with `O_EXCL` (a planted link is refused), and `nhe_o_close` deletes them. (3) `nhe_o_init_with_paths` resolves relative paths once (`getcwd`), limits the WAL path to `507` bytes (room for `".ckpt"`), creates missing files with a directory `fsync`, and refuses aliased database / WAL / checkpoint paths (`stat` device + inode) and swapped arguments. (4) New exports `nhe_o_close` and `nhe_o_checkpoint`; `nhe_o_kv_del` takes `now_sec`; `nhe_o_rag_query_nd` reports the bytes written; empty documents are rejected. (5) `nhe_o_lib.gpr` builds without `-gnata`: every assertion is discharged by `gnatprove`, while executing whole-engine `'Old` copies cost up to ~0.85 MB of stack per frame and an assertion exception cannot cross the C ABI anyway; run-time checks stay on, and the verification executable keeps `-gnata`. The deepest call needs about 256 KiB of stack (1 MiB recommended).
- **Why:** Round 12 reproduced stack overflows (`Storage_Error`) from ~0.5 MB frames, lost writes and assertion aborts under concurrent Python use, two Python engines silently sharing one state, predictable `/tmp` files wiped or followed through symlinks, and output-length/ABI mismatches.
- **Consequences:** ABI version `0.4` (`nhe_o_version_minor = 4`), documented in `include/nhe_o.h`; GNAT's signal handlers installed at load time are documented for hosts with their own handlers. Round 14: the library resets `SIGABRT` to its default action while `Nhe_O.C_API` is elaborated (otherwise a host's `abort()` / failed `assert()` became "raised PROGRAM_ERROR" and exit status `1`; `pragma Interrupt_State` was rejected because it links the tasking run time and starts a thread), the Python SDK restores the interpreter's dispositions of the five signals after loading, and the library is built with `-fstack-check` so an undersized host stack always hits its guard page. Round 15: the library is linked with `-z nodelete`, because GNAT's handlers and the loading thread's alternate signal stack (`sigaltstack`, inside `libgnat`) would point into freed memory after a `dlclose`. Process ownership of a database is `ADR-020`.

## ADR-014 — Slot-Hinted KV WAL Frames & Redis-Exact DEL / INCRBY Semantics
- **Date:** 2026-10-20
- **Decision:** `"KVMG"` SET frames carry the store slot the SET landed in (byte 8, `1 .. 64`; `0` for legacy frames and DEL), and `Recover_KV_From_WAL` applies each hinted frame to exactly that slot, so silent LRU / expired-slot evictions are reproduced. `Del` / `Del_Durable` take a timestamp: `Removed` is True iff the key was live at that time (Redis reply count), while a frame is logged whenever any slot (live or expired) is freed. Integer values follow Redis `string2ll` (no `+`, no leading zeros, no `-0`). `Write_KV_Snapshot` serializes the store for checkpoints.
- **Why:** Replay without the slot hint chose different eviction victims than the run (GETs update LRU state without being logged), so recovery could resurrect evicted keys or lose live ones.
- **Consequences:** Amends `ADR-007` and `BR-004`; old WALs without hints still replay through slot selection.

## ADR-015 — PostgreSQL-Exact JSONB Containment, UTF-8 Validation & Uniform Ingest Limits
- **Date:** 2026-10-20
- **Decision:** `@>` is one fuel-bounded recursive walker (`Value_Contains`) that follows PostgreSQL's `JsonbDeepContains` at every depth (replacing the depth-4 ladder and its raw-text fallback); numbers compare exactly through a canonical form; `\u` escapes decode UTF-16 surrogate pairs, lone surrogates and invalid UTF-8 are rejected, in keys as in values (`Is_Valid_JSONB_Key`); `->>` reports JSON `null` through `Is_Null`. Ingest limits are uniform: JSON texts and stored values at most `512` bytes (a document built field by field through the Ada API may hold up to `16` such values, kept in its `"RMET"` chain), at most `16` distinct top-level keys (duplicates keep the last value), keys `1 .. 64` bytes at every depth (empty keys rejected), at most `64` nesting levels including the root, and PostgreSQL 16 `numeric_in` range rules.
- **Why:** Round 12 found containment results that differed from PostgreSQL (false matches through the raw-text fallback, arrays deeper than three levels), CESU-8 output for surrogate pairs, accepted invalid UTF-8, and documents accepted at ingest that `@>` could never match.
- **Consequences:** Codified in `BR-003`. Metadata stored by an older build that breaks the new rules (invalid UTF-8, strings over 510 bytes, out-of-range numbers, bad nested keys) now fails recovery with `Status_IO_Error` instead of being re-ingested silently (0.x format, no version bump). Every `Status_Invalid_Syntax` rule (syntax, then an object root, then empty keys) is checked before the ingest limits, so such text is never `Status_Capacity_Exceeded`. `->` / `->>` return strings exactly as PostgreSQL does, but numbers, objects and arrays as their stored input literal: jsonb-equal to PostgreSQL's output, not always the same text (`1e2` for `100`, duplicate keys kept), because a byte-exact rendering of every accepted number cannot fit in `512` bytes (`1e131071` prints as 131 072 digits). A document ingested through the C ABI without metadata stores an empty object (`0.3` injected a hidden `{"source":"c_api"}` field).

## ADR-016 — Fail-Closed Token-Level SQL Validator With a Documented Dialect
- **Date:** 2026-10-20
- **Decision:** `Nhe_O.SQL` tokenizes like PostgreSQL's scanner (standard strings with `''`, `E''` escapes, `N''` / `B''` / `X''`, `$tag$` quoting, nested `/* */`, `--` comments, delimited identifiers with `""`) and validates statements on tokens, at their own parenthesis level, against the dialect stated at the top of `nhe_o-sql.ads` (SELECT with set operations, WITH, joins, LIMIT / OFFSET / FETCH / locking; INSERT / UPDATE / DELETE with ON CONFLICT and RETURNING; CREATE TABLE with constraints; BEGIN / COMMIT / ROLLBACK; LISTEN / NOTIFY). Everything outside it, NUL bytes, more than one statement, and data-modifying CTEs fail closed with `Status_Invalid_Syntax`.
- **Why:** Substring keyword heuristics let dollar-quoted and `E''` strings smuggle a second statement past the multi-statement guard, mis-detected clauses inside subqueries, and rejected common valid PostgreSQL. As a pre-flight guard in front of PostgreSQL, the descriptor must never claim `Status_Ok` for input PostgreSQL would run differently.
- **Consequences:** The descriptor gained `Has_Param_Limit`, `Has_Offset`, `Offset_Value`, `Has_Param_Offset`; `Has_Limit` means a literal row cap. A quoted literal continued on a later line (scan.l "quotecontinue": an `E''` literal keeps its escape mode across the newline, which once let `E'a'` + newline + `'\''; DROP ...` hide a second statement) is rejected rather than re-lexed (Round 14). The query must be well-formed UTF-8 and follows PostgreSQL 16's lexer (a vertical tab is not whitespace): the lexer works on bytes, so in client encodings whose multi-byte characters can contain a backslash byte (SJIS, BIG5, GBK, GB18030) an `E''` literal would end elsewhere than on the server (Round 15). `Execute_Hybrid_RAG_Query` applies `LIMIT` / `FETCH FIRST` / `OFFSET` within the `8`-hit ranking depth and rejects `LIMIT $n` / `OFFSET $n` (the query vector is its only bound parameter).

## ADR-017 — Exact Top-K Retrieval at Bounded Capacity & Lossless B+Tree Delete Repair
- **Date:** 2026-10-20
- **Decision:** `Search_KNN` uses the HNSW graph only to order and cache candidate distances, then evaluates every remaining active node of the query dimension and selects the exact top-K by `Node_Distance` (ties to the lower node id); for more than 64 dimensions that distance uses the nodes' 64-D `Float32` / `Int8` prefix (binary vectors use every bit), and the full-vector exact ranking is RAG Stage 2. `Delete_Key` rebuilds a densely packed tree from the surviving entries when a non-root leaf underflows, committing the rebuild only after verifying the leaf chain holds exactly `Total_Keys` ascending keys; `Insert_Key` leaves the tree unchanged on failure. `Cosine_Distance` normalizes each vector by its largest component first, so it is scale invariant.
- **Why:** At the engine's fixed capacities (32 HNSW nodes, 16 documents) approximate search missed live nodes, and the old delete repair lost keys once the tree held about 47 keys.
- **Consequences:** Retrieval is exact by construction (the cost is linear in the 32-node capacity). `Range_Scan` and `Restore_Vector_Node` gained overloads reporting `Truncated` / `Status`.

## ADR-018 — Exact `"VTS2"` Vector TOAST Payload (IEEE 754 binary32 Words)
- **Date:** 2026-10-20
- **Decision:** `Encode_Vector_TOAST` writes `"VTS2"` payloads: the 8-byte header (`"VTS2"` + big-endian `Dim`) followed by each component's IEEE 754 binary32 bit pattern (negative zero written as `+0.0`), big-endian, computed arithmetically by exact doublings (`Float_Bits`) and decoded by exact halvings in `Long_Float` (`Bits_Float`), so no `Unchecked_Conversion` to `Float` is needed. Decoding rejects infinities, NaNs and magnitudes above `Max_Component`. Legacy `"VTST"` scaled-decimal payloads stay readable. The full embedding of every document is stored at every dimension and Stage-2 re-ranks every visible candidate from it.
- **Why:** The scaled-decimal `"VTST"` words kept about 7 significant digits and flushed magnitudes below `5e-29` to zero, so Stage-2 "exact" re-ranking and recovery ranked a different vector than the one ingested (a document queried with its own embedding came back at a non-zero distance, and a flushed component could flip its binary-quantization bit).
- **Consequences:** Stage-2 distances and recovered HNSW nodes use the identical stored vector. The payload size is unchanged (`8 + 4 * Dim` bytes); databases written by `0.3` keep their legacy precision until a document is re-ingested.

## ADR-019 — First-Fit TOAST Page Allocation With Reserved Staged Pages
- **Date:** 2026-10-20
- **Decision:** `Ingest_Document` places each TOAST chain (parent chunk, vector, `"RMET"`) on the lowest run of free pages from page `10` (`Find_TOAST_Range`; the candidates are page `10` and the end of every reserved range). Reserved are the current and prior chains of every document, the chains the updated document keeps as its prior, the chains already chosen for the new version, and the pages any other active transaction staged: each document slot records the hull of the pages its uncommitted writer staged there (`Staged_Tx`, `Staged_First`, `Staged_End`), superseded versions included, until that transaction commits or aborts; a slot whose staged pages belong to another active transaction is also a write conflict. A transaction may reuse pages it staged itself. `Next_TOAST_Pg` becomes the high-water mark of reserved pages.
- **Why:** Round 13 found that the pages of a version superseded inside an active transaction were released while its WAL frames remained, so a concurrent transaction could commit on the same pages and the first one's commit then overwrote them with stale bytes, leaving the database unrecoverable. Separately, pages below the high-water mark were only reused by the same document, so a document updated an odd number of times between checkpoints grew the file without bound.
- **Consequences:** Commit and redo both apply a transaction's frames in WAL order, so only cross-transaction sharing of staged pages was unsafe; it is now impossible by construction. The database file stops growing under steady update and checkpoint cycles. Allocation scans at most about 120 candidates per chain, bounded by the 16-document capacity.

## ADR-020 — One Process per Database: `flock`-Locked Files, Per-Process Engine Ownership, Page-0 Database Check & Resolved Paths
- **Date:** 2026-10-21
- **Decision:** (1) `nhe_o_init_with_paths` (and `nhe_o_init` for its scratch files) takes exclusive non-blocking `flock(2)` locks on the database and the WAL (`Nhe_O.IO.Lock_File`) and holds them until `nhe_o_close` or the next init; a second open of either file, from any process or through a second descriptor in this one, fails with `NHE_O_STATUS_IO_ERROR` before recovery touches anything. `Lock_File` checks after `flock` that the path still names the locked file (`fstat` against `stat`), so a rename between `open` and `flock` cannot leave the lock on an unlinked file. The checkpoint locks `"<wal>.ckpt"` before renaming it over the WAL and then releases the old WAL's lock, so the WAL lock never lapses. (2) The engine records the process that opened it (`G_Owner_Pid`): in any other process (a forked child) every stateful export returns `NHE_O_STATUS_NOT_INITIALIZED`, and `nhe_o_close` or a new open only drop the inherited state and lock descriptors, without a checkpoint and without deleting scratch files; the Python SDK does this from an `os.register_at_fork` child hook. (3) An existing non-empty database file whose first `min (size, 4096)` bytes are not all zero is refused with `NHE_O_STATUS_INVALID_ARG` and left untouched, since the engine never writes page `0`; this replaces the WAL-magic check for swapped arguments. (4) Paths are resolved with `realpath(3)` once missing files exist: directory `fsync`s and the checkpoint rename act on the real files, and a symlinked WAL stays a link. (5) `"<wal>.ckpt"` is reserved: a file there is removed only when no open holds it (it is locked first: it may be another database's WAL or database file) and it classifies as a WAL (`Check_WAL_File`, the classification of `Repair_WAL_Tail` without truncation); otherwise the open (`NHE_O_STATUS_IO_ERROR` when held, `NHE_O_STATUS_INVALID_ARG` when not a WAL) or the checkpoint (`NHE_O_STATUS_IO_ERROR`) is refused. Likewise `nhe_o_init` removes an existing scratch file only when no open holds it (a process with the same pid in another PID namespace may share `/tmp`), and the checkpoint keeps the lock of its new WAL in the global `G_Ckpt_Lock`, so a child forked mid-checkpoint releases it on close (Round 15). (6) A database written with another dimension reports `NHE_O_STATUS_DIMENSION_MISMATCH`.
- **Why:** Round 14 reproduced two processes (multi-worker servers, `multiprocessing` fork children) opening one database and silently losing acknowledged commits, or leaving it unopenable; a mistyped `db_path` that truncated the user's file and was then overwritten by commits; a checkpoint that replaced a symlinked WAL with a regular file, so a later restore of the link lost commits; and a user file at `"<wal>.ckpt"` deleted at open.
- **Consequences:** The locks are advisory: tools that ignore `flock` can still change the files, and a file system without `flock` support fails the open (fail closed). A forked child must call `nhe_o_close` (or `exec`) to release its inherited lock descriptors if the parent is to reopen the database while the child runs, and hosts must not fork while a call is in flight (the SDK holds its engine lock across `fork()` through `os.register_at_fork`). `Get_Process_Id` is modelled as a constant (`Global => null`): the process identity changes only at `fork()`, between calls, and no contract relates its values across calls. A foreign file whose first 4 KiB happen to be zero (some disk images) passes the page-0 check. Hard-linked WALs are not supported: a checkpoint replaces only the name in use. The Ada API (`Nhe_O.RAG`, `Nhe_O.KV`) takes no locks; its callers own their files. The page-0 check relies on page `0` never being written: the page-0 system catalog planned for Epic 05 must replace it with a check of that catalog page.
