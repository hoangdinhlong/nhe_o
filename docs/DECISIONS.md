## ADR-001 — Unified Multi-Model Engine (PostgreSQL SQL/JSONB/Vector + Redis KV & Pub/Sub over Shared MVCC/WAL)
- **Date:** 2026-10-16
- **Decision:** Build Nhé O (crate `nhe_o`, Ada root package `Nhe_O`) as a single in-process multi-model engine where PostgreSQL relational tables, `VECTOR(d)` embeddings, `JSONB` documents, and Redis-compatible Key-Value cache entries share a unified 4096-byte slotted-page layout, header-and-payload CRC32-verified Write-Ahead Log (WAL), and MVCC snapshot isolation (`xmin`/`xmax`), paired with a bounded ring-buffer Pub/Sub broker.
- **Why:** Running separate SQLite, `pgvector`, and Redis processes for embedded or local-first workloads adds operational overhead and cross-store consistency bugs. Sharing one ACID storage and WAL engine guarantees crash-safe durability across relational, vector, document, and KV mutations while allowing direct KV and Pub/Sub calls to bypass SQL parsing overhead.
- **Consequences:** `Nhe_O.Types` defines the canonical PostgreSQL type tags shared across SQL, KV, and JSONB subsystems; `Nhe_O.Transaction` governs monotonic transaction IDs (`Tx_Id`), WAL frame encoding/decoding/verification, and MVCC visibility across all models.

## ADR-002 — 100% SPARK_Mode (On) Mandate via Statically Bounded Memory and Contract-Bound POSIX Syscall I/O
- **Date:** 2026-10-16
- **Decision:** Enforce `pragma SPARK_Mode (On);` across 100% of specifications, bodies, and entrypoints (`src/*.ads` and `src/*.adb`, 26/26 files). Use statically bounded containers (zero dynamic heap allocation) and bind `Nhe_O.IO` (`src/nhe_o-io.ad[sb]`) directly in `SPARK_Mode (On)` (`Convention => C, Import => True, Side_Effects`) to atomic, exception-free POSIX syscalls (`open`, `pread`, `pwrite`, `lseek`, `fsync`, `close`, `unlink`) and `Ada.Text_IO`.
- **Why:** Standard Ada file libraries (`Ada.Direct_IO`, `Ada.Streams.Stream_IO`) report I/O errors by raising Ada exceptions, which would force the physical I/O body out of SPARK (`SPARK_Mode (Off)`). Binding directly to POSIX C syscalls — which never raise Ada exceptions and instead return explicit status/byte counts (`int` / `ssize_t`) — keeps 100% of I/O orchestration (`To_C_Path`, embedded-NUL path rejection, 64-bit page offset bounds `Valid_Page_Id`, short-read/write detection, bounded `EINTR` retry loops, and `fsync` checks) inside `SPARK_Mode (On)`.
- **Consequences:** Zero files in `src/` may use `pragma SPARK_Mode (Off);` (`BR-001`, mechanically enforced by `SELF-AUDIT.md` check `B5`). All buffers, pages, vectors, JSONB documents, KV slots, and Pub/Sub rings use fixed capacity bounds without exception propagation. *(See lesson: [`learning/swe/01-contract-bound-posix-syscalls-in-spark.md`](learning/swe/01-contract-bound-posix-syscalls-in-spark.md)).*

## ADR-003 — 4KB Slotted Pages with TOAST Overflow Chains, 4096-D Vectors & Quantization for Universal RAG
- **Date:** 2026-10-17
- **Decision:** Retain 4096-byte primary slotted pages while introducing PostgreSQL-style TOAST overflow page chains (`Overflow_Page_Id`) for oversized attributes (high-dimensional embeddings and parent-document RAG chunks), expanding `Max_Vector_Dim` up to `4096`, and supporting Scalar (`Int8`) and Binary (`1-bit` Hamming) vector quantization alongside `Float32` (`<->`, `<=>`, `<#>`) for HNSW and Hybrid RAG.
- **Why:** Local LLM workflows (e.g., Qwen 3.8 27B, Qwen 3.8 35B-A3B) and modern embedding models (`bge-m3` 1024-D, `text-embedding-3-large` 3072-D, `Qwen3-Embedding-8B` 4096-D = 16KB raw `Float32`) paired with multi-kilobyte text chunks exceed any single 4KB or 16KB page. Keeping 4KB primary pages aligns with OS/NVMe page boundaries and allows fast relational/JSONB metadata filtering over compact 16-byte TOAST pointers without reading cold vector payloads, while `Int8`/Binary quantization reduces HNSW RAM usage by 4x–32x so the database coexists with large local LLMs.
- **Consequences:** Resolves `Q-001`. `Nhe_O.Transaction` gains linked 4KB TOAST overflow pages (`BR-006`); `Nhe_O.Vector` scales up to 4096 dimensions with `Float32`, `Int8`, and `Binary` quantization (`BR-003`) in Epic 02. *(See lesson: [`learning/ai/01-toast-overflow-and-vector-quantization-for-local-llm-rag.md`](learning/ai/01-toast-overflow-and-vector-quantization-for-local-llm-rag.md)).*

## ADR-004 — Dual-Mode Pub/Sub: Fast In-Memory Ring Buffers + Optional `DURABLE` WAL-Committed Dispatch
- **Date:** 2026-10-17
- **Decision:** Support two delivery semantics in `Nhe_O.PubSub`: (1) default low-latency in-memory ring-buffer delivery (Redis `PUBLISH`/`SUBSCRIBE` semantics), and (2) optional `Durable` transactional delivery (PostgreSQL `LISTEN`/`NOTIFY` semantics) where staged notifications are dispatched to subscribers only after `Nhe_O.Transaction.Commit_Tx` flushes the transaction's WAL frame to disk, or discarded on `Rollback_Tx`.
- **Why:** Agentic RAG and local LLM applications require both instantaneous ephemeral event streaming between agents and crash-safe transactional triggers (ensuring background RAG embedding/HNSW workers never index uncommitted or rolled-back document chunks).
- **Consequences:** Resolves `Q-002`. `Nhe_O.PubSub` and `Nhe_O.Transaction` coordinate transactional notification staging and post-WAL-commit dispatch (`BR-005`) in Epic 02. *(See lesson: [`learning/swe/02-transactional-pubsub-wal-commit-barrier.md`](learning/swe/02-transactional-pubsub-wal-commit-barrier.md)).*

## ADR-005 — Formally Verified C ABI / FFI Boundary via Precondition-Free Defensive Subprograms in 100% SPARK
- **Date:** 2026-10-17
- **Decision:** Expose the embedded C / Python Foreign Function Interface (`Nhe_O.C_API` in `src/nhe_o-c_api.ad[sb]`, C header `include/nhe_o.h`, Stand-Alone Shared Library `nhe_o_lib.gpr` -> `lib/libnhe_o.so`, and Python SDK `bindings/python/nhe_o.py`) in 100% `pragma SPARK_Mode (On);` using fixed-capacity `Interfaces.C.char_array` buffers paired with explicit integer lengths and precondition-free (`Pre => True`) exported procedures that defensively validate every untrusted C argument before invoking internal SPARK engines.
- **Why:** Raw C pointers (`Interfaces.C.Strings.chars_ptr`) violate SPARK's ownership and aliasing model and would force `SPARK_Mode (Off)`, while placing SPARK `Pre` contracts on exported `Convention => C` subprograms cannot be statically verified against external C or Python callers. Passing fixed-bound `char_array` buffers by reference (`const char *` / `char *` in C ABI) and validating all scalar lengths, ranges, and floating-point bounds inside the exported wrapper guarantees that `gnatprove` proves 100% Absence of Run-Time Errors (AoRTE) across the FFI boundary regardless of what values an external caller passes.
- **Consequences:** All 26 source files (`src/*.ads` and `src/*.adb`) remain in 100% `SPARK_Mode (On)` (`BR-001`) and achieve 100% formal verification (`0 unproved` checks in `gnatprove`), while Python (`ctypes`), C, C++, and Rust applications can load `lib/libnhe_o.so` directly. *(See lessons: [`learning/swe/03-precondition-free-defensive-c-ffi-in-spark.md`](learning/swe/03-precondition-free-defensive-c-ffi-in-spark.md), [`learning/swe/04-proving-ieee754-float-and-loop-invariants-in-spark.md`](learning/swe/04-proving-ieee754-float-and-loop-invariants-in-spark.md)).*

## ADR-006 — NO-STEAL WAL Staging, 2-Pass Committed-Only WAL Recovery, Unified 8192-Entry CLOG, Primary `"SLOT"` Pages & `"VTST"` / `"RMET"` TOAST Chains
- **Date:** 2026-10-17 (Updated 2026-10-19)
- **Decision:** (1) Enforce **NO-STEAL** page persistence (`R2-CRIT-01`, `R3-CRIT-02`): `Write_TOAST_Chain`, `Ingest_Document`, and `Delete_Document` stage 4KB `"TOAS"` and `"SLOT"` pages exclusively as `WAL_Frame_Data` (`0`) frames in `.wal` while `Ctx.State = Tx_Active`, and `Commit_Tx` pre-scans all frames up to `Max_WAL_Scan_Frames = 4096` (`Hit_EOF` check), verifies `Verify_WAL_Frame` CRC32 on every frame (`R3-CRIT-02`), and materializes staged pages to `.db` only after flushing the `WAL_Frame_Commit` (`1`) barrier frame; (2) unify `Max_CLOG_Entries = Max_Tx_Id = 8192` (`R3-CRIT-01`), initialize `Default_CLOG := [others => Tx_Idle]`, and run `Redo_WAL_Recovery` in two passes (Pass 1 discovers `WAL_Frame_Commit` records; Pass 2 replays only committed transactions); (3) persist primary tuples in 4096-byte `"SLOT"` slotted pages (`240 B` tuple cell / `208 B` `Inline_Data`) paired with optional `"RMET"` extended summary + JSONB metadata TOAST chains (`R3-HIGH-04`, lossless up to `512 B` summary + `16 × (64 B key, 512 B val)` JSONB) and pairwise non-overlapping `Ranges_Overlap` / `Is_TOAST_Range_Free` page allocation (`R3-CRIT-03`); and (4) combine Stage-1 HNSW routing (64-D Matryoshka `Float32`/`Int8` with `Int8_Scale` + 4096-D `Binary`, synchronized across `Insert_Vector`/`Remove_Vector`/`Restore_Vector_Node`, `R3-HIGH-02`, `R3-MED-04`) with Stage-2 Exact L2 Re-Ranking from `"VTST"` 4KB TOAST overflow chains (`8B` `"VTST"` + `Dim` header + 15-tier scientific `Float32` words retaining 7–8 significant decimal digits up to `16,392` bytes, `R2-HIGH-02`, `R3-MED-02`).
- **Why:** Writing dirty pages directly to `.db` before `Commit_Tx` without an `UNDO` log or defaulting `CLOG` to `Tx_Committed` violates ACID atomicity and snapshot isolation (`CRIT-01`, `CRIT-04`, `CRIT-05`, `R2-CRIT-01`, `R3-CRIT-01`, `R3-CRIT-02`). Furthermore, persisting full `> 64`-D `Float32` embeddings in `"VTST"` TOAST chains and full `Summary_Text`/`Metadata` in `"RMET"` TOAST chains (`Q-003`, `CRIT-07`, `R2-HIGH-02`, `R3-HIGH-04`) while keeping compact 64-D + 1-bit representations in RAM gives HNSW sub-millisecond RAM efficiency without sacrificing exact 4096-D top-$K$ precision or truncating document metadata on Page 1.
- **Consequences:** Resolves `Q-003` and remediates `CRIT-01`, `CRIT-04`, `CRIT-05`, `CRIT-07`, `R2-CRIT-01`, `R2-HIGH-01`..`R2-HIGH-03`, `R3-CRIT-01`..`R3-CRIT-03`, `R3-HIGH-02`, `R3-HIGH-04`, and `R3-MED-02`..`R3-MED-04`. Codified in `docs/domain/storage-and-wal-format.md` and `BR-002` / `BR-006`. *(See lessons: [`learning/swe/05-two-pass-wal-recovery-and-slotted-page-crc32-in-spark.md`](learning/swe/05-two-pass-wal-recovery-and-slotted-page-crc32-in-spark.md), [`learning/swe/06-two-stage-toast-vector-reranking-and-hnsw-pruning.md`](learning/swe/06-two-stage-toast-vector-reranking-and-hnsw-pruning.md)).*

## ADR-007 — Dual-Mode Key-Value Store (In-Memory Cache + `"KVMG"` WAL-Before-Data Persistence) & Feature → Grooming Epic Cadence
- **Date:** 2026-10-17 (Updated 2026-10-19)
- **Decision:** (1) Keep `Nhe_O.KV.Set`/`Get`/`Del`/`Expire`/`Incr_By` as `Global => null` in-memory operations for sub-microsecond Redis cache workloads while adding `Set_Durable`, `Del_Durable`, `Expire_Durable`, `Incr_By_Durable`, and `Recover_KV_From_WAL` (`WAL_Frame_KV` with `"KVMG"` page magic, IEEE 802.3 CRC32, `Store := Saved_Store` rollback on WAL write failure (`R3-HIGH-03`), dedicated `G_Next_KV_Seq` sequence numbering in `Nhe_O.C_API` decoupled from MVCC `G_Next_Tx` (`R3-CRIT-01`), and `Max_Frames` overflow / torn-file detection (`R2-HIGH-05`, `R3-HIGH-01`)) for crash-recoverable KV state (`Q-004`); and (2) adopt a mandatory **Feature Epic → Grooming Epic** cadence in `AGENTS.md` and `docs/epics/README.md` so every feature epic milestone is audited (`ADVERSARIAL-REVIEW.md`) and hardened before the next feature epic begins.
- **Why:** Callers using `Nhe_O.KV` as an ephemeral session/rate-limit cache need zero syscall overhead (`Global => null`), whereas callers storing durable application configuration or counters need strict `WAL-before-Data` crash recovery without depleting MVCC transaction IDs. Similarly, alternating feature epics with grooming epics prevents subtle semantic/durability debt from compounding beneath 100% AoRTE proofs.
- **Consequences:** Resolves `Q-004` and remediates `HIGH-08`, `R2-CRIT-02`, `R2-HIGH-05`, `R3-CRIT-01`, `R3-HIGH-01`, `R3-HIGH-03`, and `R3-LOW-04`. Epic 04 (`04-post-epic-03-grooming-and-hardening`) is now 100% complete across all three adversarial audit rounds (58/58 findings remediated).

## ADR-008 — Native Labeled Property Graph Engine (`Nhe_O.Graph`), Bi-Directional CSR Adjacency (`"GRPH"`), `SQL/PGQ MATCH` & Multi-Hop GraphRAG
- **Date:** 2026-10-19
- **Decision:** Upgrade Nhé O from a single-edge `1-Hop Related_Doc_Id` pointer to a first-class, 100% formally verified **Labeled Property Graph (LPG) Engine (`Nhe_O.Graph`)** on par with Neo4j and Apache AGE in core graph power, scheduled as **Epic 06 (`06-property-graph-and-multi-hop-graphrag`)** immediately after Epic 05 (`Catalog`, `Buffer_Pool`, `Executor`):
  1. **Data Model & Storage (`"GRPH"` 4KB Pages + MVCC)**: Support typed Vertices (`Vertex_Id`, `Label`, `JSONB_Document` properties, optional `Vector_Id` / `Doc_Id` binding, `MVCC_Tuple_Header`) and Directed Weighted Edges (`Edge_Id`, `Src_Vertex`, `Dst_Vertex`, `Edge_Label`, `Float32 Weight`, `JSONB_Document` properties, `MVCC_Tuple_Header`) persisted in 4096-byte CRC32-verified `"GRPH"` pages managed by `Nhe_O.Buffer_Pool` and `Nhe_O.Transaction` (`NO-STEAL` WAL + `CLOG`).
  2. **Bi-Directional Index-Based Adjacency (`Out_Edges` & `In_Edges` / CSR)**: Maintain $O(1)$ outgoing and incoming edge chains per vertex via array indices (`First_Out_Edge`, `Next_Out_Edge`, `First_In_Edge`, `Next_In_Edge`).
  3. **Core Graph Operators & `Always_Terminates` Proofs**: Implement multi-hop pattern matching (`1..k` hops, outgoing `->`, incoming `<-`, bidirectional `-`), variable-length reachability (`BFS` with vertex/edge label and `JSONB @>` predicates), unweighted & weighted Shortest Path (`BFS` / `Dijkstra`), Mutual Neighbors / Triangle Discovery ($N(u) \cap N(v)$ for social graphs and community detection), Degree/PageRank centrality, and **Multi-Hop GraphRAG Score Propagation** coupled with 4096-D `Nhe_O.HNSW`.
  4. **Query Surface (`SQL/PGQ MATCH` + Native Composable FFI API)**: Support ISO SQL:2023 `SQL/PGQ` `MATCH (a:Label)-[e:TYPE*1..k]->(b:Label)` patterns directly inside `Nhe_O.SQL` (`SELECT ... MATCH ... WHERE meta @> ... ORDER BY emb <=> $1`) alongside zero-parse-overhead C ABI / Python SDK primitives (`nhe_o_graph_upsert_vertex`, `nhe_o_graph_upsert_edge`, `nhe_o_graph_traverse_bfs`, `nhe_o_graph_shortest_path`, `nhe_o_graph_mutual_neighbors`, `nhe_o_rag_graph_query`).
- **Why:** A true Property Graph pillar serves both as a standalone capability (Social Networks, ReBAC permissions, Fraud/Lineage graphs) and as a **force multiplier for every original Nhé O pillar**: it elevates `Nhe_O.RAG` from flat vector lookup to true multi-hop Knowledge GraphRAG, eliminates expensive recursive SQL `JOIN`s in `Nhe_O.SQL`/`Nhe_O.BTree` via $O(1)$ adjacency hops, pairs with `Nhe_O.KV` for real-time per-vertex counters/TTL state, and enables graph-routed notifications in `Nhe_O.PubSub` — completing the 5-model embedded architecture (`Relational + JSONB + 4096-D Vector + Property Graph + Redis KV/PubSub`) in a single `< 300 KB` `100% SPARK_Mode (On)` library.
- **Technical Challenges / Disadvantages & Formal Mitigations:**
  1. **SPARK Anti-Aliasing Mandate vs. Heap Pointer-Chasing**: Neo4j relies on Cyclic Heap Pointers ("index-free adjacency"), which SPARK forbids (`BR-001`). *Mitigation:* Use KùzuDB-style **Array-Indexed Double-Linked Adjacency Lists / Compressed Sparse Row (CSR)** over 4KB `"GRPH"` pages, which is 100% SPARK-provable, eliminates dangling pointers, and improves CPU L1/L2 cache locality over JVM pointer chasing.
  2. **Cypher Scripting Surface Bloat vs. Parser VC Complexity**: Implementing all of Neo4j's `openCypher` scripting conveniences (`UNWIND` list comprehensions, `APOC` procedures, arbitrary multi-`WITH` pipelines) would bloat the parser and slow down `gnatprove`. *Mitigation:* Support the declarative core via ISO SQL:2023 `SQL/PGQ` `MATCH (a)-[e]->(b)` inside `Nhe_O.SQL` while exposing composable native graph operators over the in-process C ABI / Python SDK (zero TCP round-trip overhead).
  3. **Static RAM Footprint Risk if Coupled into `RAG_Engine`**: Embedding multi-edge adjacency arrays inside every `RAG_Document_Entry` would inflate `RAG_Engine` for non-graph workloads. *Mitigation:* Build `Nhe_O.Graph` as a decoupled sibling package (`src/nhe_o-graph.ad[sb]`) backed by 4KB `"GRPH"` pages through Epic 05's `Nhe_O.Buffer_Pool`, leaving existing `KV`, `Vector`, `HNSW`, and basic `RAG` footprints untouched.
  4. **Cyclic Graph Infinite Loops & SMT Solver Timeouts**: Cyclic graphs (`A -> B -> A`) can hang naive traversals and explode SMT proof obligations. *Mitigation:* Enforce iterative bounded-queue `BFS` / `Dijkstra` with explicit `Visited_Vertex_Set` boolean arrays, decreasing `Loop_Variant`s (`Always_Terminates`), and modular helper contracts (`with Post => ..., Global => null`, per Lesson 07).
- **Consequences:** Codified in `BR-008`, `VISION.md`, `ARCHITECTURE.md`, Lesson 08 (`docs/learning/swe/08-formally-verified-property-graph-csr-and-sql-pgq-in-spark.md`), and scheduled in `docs/epics/06-property-graph-and-multi-hop-graphrag/PROGRESS.md`.
